# Private WebView IPC acceptance slice

This isolated test slice is not a replacement for the production Windows shell. The existing production bootstrap race remains unresolved, and the loopback forwarding prototype remains disabled and untouched.

`tests/private-webview-ipc.test.js` compiles and runs a real WebView2 harness. It loads the repository's `public/index.html` and assets using an intercepted private origin; all other resource requests are blocked by the harness. A page request for the read-only `/api/auth/devices` operation is delivered through the C# harness to the exact Node child it launched, over inherited standard-input and standard-output pipes using `NativeIpcClient` and `serveNativeIpc` framed messages. The child uses the same `listAuthorizedIdentityDevices` service as the HTTP route. The test creates a synthetic Owner, signs a real Ed25519 challenge, and holds the resulting session exclusively in the child process. It tests rejection of an invalid session, a Limited device, and a revoked session. A POST mutation is blocked rather than bypassing CSRF.

The tests cover backend exit, an input-pipe disconnect while the child is still alive, and abrupt termination of the harness. They check that an attacker-controlled loopback listener sees no connection during the test and after termination. The synthetic Owner, isolated database, WebView profile, and child are test fixtures; no existing Owner profile is accessed or migrated. The harness is not included in the production build, and its test protocol is not a hardened general-purpose IPC implementation.

Before this design can replace production bootstrap it still needs an authenticated existing-Owner login and verified migration of origin-bound WebView2 keys, bounded and correlated IPC framing, authenticated navigation and resource policy hardened for production assets and frames, crash and child cleanup guarantees beyond this fixture, CSRF-equivalent handling for any future mutating operations, and real in-window end-to-end validation. Until those are complete, do not enable the slice as the shipping shell or claim the bootstrap release gate is satisfied.

The harness uses WebView2's source-kind-aware resource filter for all request source kinds. Its real WebView2 test separately exercises page, dedicated-worker, and service-worker loopback requests. This is test evidence for those cases only; shared workers, existing profile state, and every other request path still need adversarial verification before production use.

`tests/private-origin-key-continuity.test.js` uses a separate isolated WebView2 profile to create a non-extractable Ed25519 key under the legacy localhost origin, closes the harness, reopens the same profile, and checks that the same public key is available. It generates a different non-extractable key under the private origin and verifies signatures from both keys over a synthetic statement binding their public keys. It does not enroll the new key, migrate an actual Owner or credential, or implement a production migration protocol. WebView2 made loopback TCP connections despite request interception, and an implicit `/favicon.ico` request reached the listener in an earlier version of the test. The test's controlled page now supplies a data-URL icon and restrictive content policy; with a synthetic legacy session cookie present, the listener observed connections but no data bytes. Migration must account for browser connection behavior, stale service workers and caches, and the confidentiality and authorization of every request; resource interception alone is not evidence that no network connection occurs.
